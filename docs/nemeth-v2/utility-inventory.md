# Utility inventory -- what a student can actually write

Generated by `scripts/nemeth-utility.mjs` (`npm run nemeth:utility`) and enforced by
`test/unit/nemeth/utility-gate.test.js`. Do not hand-edit -- re-run the script instead.
Every row runs through the public `parseNemeth`, so this measures the API the app calls.

This is the **second** gate. `coverage.md` grades the parser against 613 externally-
verified corpus cases and measures **correctness**; this file measures **usefulness**, and
the two came apart badly once already: at PASS 177 / ERROR 0 the parser still could not
write `a - b`. The corpus is a rule-conformance suite, so frequency in it counts how many
rules touch a symbol, not how often anyone uses one. **The corpus grades; this inventory
plans.**

## The standing lesson

Task 5's whole ordering came from corpus refusal counts. That measured what MathCAT's and
SRE's rule-test corpora exercise, not what a student types: the minus sign ranked about
fifth and was deferred as "if budget remains" through four tasks. **Corpus coverage is not
utility.** This file is executable so that the gap cannot reopen silently -- it is
regenerated from the same run that gates the build, so the document cannot drift from the
measurement the way its hand-written predecessor did.

Adding rows is cheap, and that is the trap. Task 5a added digits and letters as pure data:
PASS +68, and **11 wrong answers**, because the data reached grammar that did not exist
yet. **Data ships with the grammar it exposes, or it does not ship** -- and the corpus gate
is what catches the difference, so run both.
